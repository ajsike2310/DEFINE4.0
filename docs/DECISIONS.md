# Decisions

1. **SQLite + `create_all`, no Alembic** — fastest to a persistent local app; SQLAlchemy keeps Postgres open. Cost: schema changes need a manual DB reset until Alembic is added.
2. **Rule-based intents, no LLM** — no verified STT/LLM access; rules are deterministic and testable. Malayalam coverage is a tiny hand-written phrase list.
3. **Demo provider returns events synchronously through the same `apply_event` path as real webhooks**, so demo exercises real dedupe/transition code.
4. **Scenario by phone last digit** for deterministic demos; demo campaigns are hard-wired to the demo provider.
5. **Consent required by default** (`require_consent=true`); unknown consent is skipped at start. CSV import needs an explicit consent confirmation.
6. **Retries only via `retry-due`** and only after technical failures; `start` never re-dials.
7. **Exotel flow-based calling** (Connect Number to Call Flow) chosen over Connect Two Numbers, which bridges an agent leg and is not an IVR campaign.
8. **E.164 required** — no guessing country codes.
9. **Phone numbers masked in UI**, masked in logs.
11. **Clarify-once is keypad-only, one attempt, operator-triggered.** Keypad answers are unambiguous; one attempt avoids pestering; operator trigger keeps a human in control until we trust automation. Auto-trigger is a later option.
12. **Exotel response path = Gather → Passthru GET** (documented `digits`/`CustomField`), not speech: no verified STT. Webhooks are token-protected because Exotel documents no signature.
13. **Headcount range, not a forecast** — no model, no calibration claim; it is arithmetic over stored outcomes.
14. **Visual language (UI refresh).** One type family (IBM Plex Sans, tabular numerals), sentence-case labels, cool paper canvas, deep teal chrome, a single raspberry attention colour, hairline-divided metric strips instead of stacks of cards, status dot-badges. Motion is limited to one orchestrated moment (dashboard load: figures count up, headcount bar fills) plus responses to actions (expanding rows, rows leaving the queue, notices, wizard steps, button press); all of it is disabled under `prefers-reduced-motion`. Deliberately avoided: serif display + cream + terracotta, tracked all-caps labels, monospace data labels, arrow-suffixed links, staggered fade-ins on every card.
15. **Notifications are client-side and derived from real events.** One `NotifyProvider` holds toasts, a persisted history (last 50, `localStorage`, guarded) and the confirm-dialog state. Actions report their outcome as a toast (errors announced with `role="alert"`, others `role="status"`, hover/focus pauses auto-dismiss, max 4 on screen, identical toasts within 1.5 s collapse). The bell is the notification centre. `window.confirm()` is replaced by an accessible dialog (Esc/backdrop cancel, focus trap, destructive actions focus *Cancel*). Live alerts poll the existing follow-up queue every 15 s (paused while the tab is hidden; first poll is a silent baseline; can be switched off in Settings) — no new backend endpoint, no push channel, and nothing is announced that is not in the data. Server push (SSE/WebSocket) or OS/browser notifications are deliberately out of scope for now.
10. **Tailwind 4 + plain components** instead of shadcn/RHF/Zod/Framer to limit dependencies.
16. **Leads are consented, not scraped; score is a checklist.** Leads come from a public sign-up page (consent box required), organiser CSV import or manual entry. Converting a lead creates a participant; revoked consent blocks conversion, and revoking after conversion opts the participant out. The readiness score is a visible points checklist (consent, source, email, language, interest), not a prediction. The sign-up endpoint is unauthenticated, like the rest of the API.
17. **Quality page reports behaviour, not accuracy.** Integrity checks count violations of enforced rules (0 = none found); AI figures describe how the rules engine behaved; the phrase check runs a small team-written synthetic set live. Duplicate provider events are rejected before storage so they are not counted.
18. **Browser demo call with ElevenLabs, because Exotel access is unavailable.** The hackathon team reported an Exotel API key problem and asked for ElevenLabs tokens to be used instead. ElevenLabs only supplies voice and speech-to-text; it is not a phone carrier, so no real phone call is placed. A dedicated `browser_demo` provider (always `is_simulated`) starts an attempt that a person completes in the browser: keypad, typed text, or a recording transcribed by ElevenLabs. The transcript is classified by the same `process_response` rules and `apply_event` path as every other reply, so opt-out wins, ambiguity is not confirmation and clarify-once still apply. A failed transcription records nothing and leaves the call open. Limited to sample (demo) campaigns so role-play never sets a real participant's outcome. The speak endpoint voices only the call's own script, never arbitrary text. The ElevenLabs key stays in `.env`; the API never returns it. Not chosen: an ElevenLabs conversational agent that talks freely, because its replies would not pass through our rule-based safeguards.
19. **Live call keeps the rules in charge; the agent never improvises.** The hands-free call loops speak, listen (browser voice-activity detection: speech start, 1.2 s of quiet ends the turn, 9 s of nothing ends the attempt), transcribe (ElevenLabs), classify (existing `process_response`), then speak a fixed closing line chosen by intent (`policies/closing_lines.py`). An information question is answered only with text the organiser approved, otherwise it is passed to a person. An unclear attendance answer triggers the existing clarify-once call, spoken once. Silence records nothing and leaves the participant as they were. Rejected: handing the conversation to an ElevenLabs agent or an LLM, because free-form replies could promise things, answer from invented facts, or treat hedging as a yes.
